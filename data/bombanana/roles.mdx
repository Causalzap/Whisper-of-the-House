<h2 id="choose-roles" className="scroll-mt-24">
  The first bad run tells me more than the role names do
</h2>

Blind, Deaf, and Mute describe what each player is missing, but the real difference appears once the timer starts.

Blind is handling the case itself. Mute has the manual. Deaf is standing in the middle, carrying the bomb state toward the manual and carrying the answer back toward the bomb.

That makes the three seats demanding in completely different ways.

I do not give Deaf to somebody just because they talk the most. That seat is much closer to short-term memory management: which module are we on, which value belongs to which position, and did the panel change after the last action?

Mute has a different pressure point. A player can understand the manual perfectly and still struggle if every answer takes ten seconds of improvised gestures to send back.

Blind needs patience as much as speed. Once the hands start moving before the answer is settled, even a completely correct lookup can end as a strike.

<h2 id="blind" className="scroll-mt-24">
  On Blind, I want the sentence to end with something my hands can do
</h2>

A color can be the correct answer on the manual side and still be an unfinished instruction on the bomb side.

Suppose the lookup says:

**Blue**

If there are several cables in front of me, I still need to work out which physical object “Blue” refers to. Under a short timer, that extra interpretation is exactly where a clean answer can become a bad input.

I would rather hear:

**“Second cable from the left.”**

The same style works on other panels:

- **top-right button**
- **press Up**
- **third slider down**
- **enter 57**
- **left selector**
- **second key**

The final call is strongest when Blind does not need to translate it again.

Blind is not only receiving instructions. Braille on the bomb can make Blind the source of information too.

That produces two separate moments: first I report what only I can read; later I perform the answer that comes back. Mixing those moments makes it easy to touch something while the other two players are still deciding what the information means.

There is also a much more basic failure that happens early: sometimes Blind has not even entered the correct interaction view yet. One group spent most of a run insisting there was nothing useful to click before discovering how to focus into the bomb properly. At that point, more rule explanation would not have helped. The physical access problem had to be solved first.

If the uncertainty is specifically which Cable target is correct, I use the <Link href="/bombanana/wire">BOMBANANA Cable / Wire Guide</Link> after the count, light, and cable order are confirmed.

<h2 id="deaf" className="scroll-mt-24">
  Deaf is where a correct number can acquire the wrong meaning
</h2>

One of the most useful failures I have seen started with a single signal:

**“Two.”**

The receiver saw the two, then saw a downward gesture, and interpreted the combination as:

**second control → down**

That was not what the sender meant. The two was part of a question about which object they were discussing.

Nothing about the number itself was false. The failure came from leaving the noun unstated.

That is the point where I stop using naked numbers.

Instead of:

**“Two.”**

I use:

**“Slider two.”**

Once that is acknowledged, the direction follows.

Instead of sending several values without anchors, I keep the object attached:

**“Second is blue.”**

**“Top-right is four.”**

**“Third slider, down.”**

The call becomes slightly longer, but the chance of binding a correct value to the wrong object drops sharply.

The improvement shows up quickly when the team retries.

In a later attempt, the same type of panel was called by position, then color, then action. Instead of one player trying to decode whether “two” meant a slot or a command, everybody knew which physical control was active before the direction arrived.

That is the kind of change I want after a communication failure: not “talk more,” but remove one specific ambiguity.

<h2 id="mute" className="scroll-mt-24">
  Mute has to finish the lookup before the hands become useful
</h2>

The manual can contain the right answer while the rest of the team still has no way to use it.

The most literal version of this happens when Mute tries to gesture with the manual still raised. The book can block the exact hand movement Deaf is waiting to read.

<Image
  src="/images/bombanana/bombanana-manual-blocks-gesture.webp"

  width={1600}
  height={900}
  className="my-8 rounded-xl"
/>

My physical rhythm on Mute is simple:

**read → decide → lower the manual → gesture**

The complicated part happens inside the book. The message coming out should be much smaller.

A question such as:

**“Second one?”**

can often end in yes or no.

A proposed direction can be confirmed or rejected.

A physical slot can be returned with fingers.

A short sequence can be sent one item at a time.

The worst question to receive is:

**“What do we do?”**

Now Mute has to identify the module, discover which fields are missing, locate the correct rule, solve it, and somehow mime the reasoning. That is far more work than receiving a complete state and returning one action.

<h2 id="signals" className="scroll-mt-24">
  We settle a tiny vocabulary before the timer gets loud
</h2>

A complicated gesture system is not useful if somebody has to remember what half the gestures mean.

Six signals cover most of the situations where our communication starts to drift.

  caption="The small signal set I keep consistent across BOMBANANA runs."

The distinction I care about most is **repeat** versus **reset**.

If everyone still agrees that we are on the same panel and only one number was missed, repeating that number is efficient.

If one player thinks the panel advanced, another still has the old color in mind, and nobody can say whether the previous action was accepted, repeating a single number is dangerous. That is a reset.

The other important command is **hands off**.

Silence should never force Blind to guess whether the team means “go ahead” or “wait.” When the call is disputed, the hands come off the panel until there is one unambiguous action.

<h2 id="perspective" className="scroll-mt-24">
  Left and right fail when two players are standing inside different coordinate systems
</h2>

Direction makes this obvious very early.

Mute or Deaf may reach the correct result:

**Left**

Blind then has to answer a different question:

**Whose left?**

Our convention is Blind's perspective while facing the bomb.

The particular convention is less important than freezing it. Switching from Blind's left to the viewer's left halfway through a session makes every later directional call suspect.

Numbering needs the same discipline.

For a horizontal row, I count from left to right.

For a grid, I put the location before the value:

**“Top-right, four.”**

That is much safer than sending “four” first and expecting everybody to remember which four is being discussed.

The visual angle matters too. A hand motion that looks like left from one player's side can look mirrored from the other side. Before the run becomes crowded, I test one directional call and keep whichever convention Blind reads correctly.

<h2 id="current-state" className="scroll-mt-24">
  A solved rule is useless once it belongs to the previous state
</h2>

Communication can fail without anyone mishearing a word.

The information can simply become old.

A light, number, direction, or sequence may have been correct when it was first read. If Blind presses something and the panel advances, the old answer no longer belongs to what is currently on screen.

After an input, I watch the panel before another answer starts moving through the team.

There are three outcomes.

**The module clears.**  
That information is finished.

**The module changes.**  
The previous values are discarded and the new state starts clean.

**Nothing changes.**  
Now we decide whether the action was incomplete, incorrect, or waiting for another step.

This is especially important on modules that change state during the solve. Calculator is a good example because the arithmetic result and the later light state are not the same moment. When the puzzle logic itself is the problem, I use the <Link href="/bombanana/calculator">Calculator Guide & Solver</Link>; on Roles, I only care that the new state does not get mixed with the old one.

<h2 id="one-module" className="scroll-mt-24">
  Two half-solved modules create more trouble than one difficult module
</h2>

The team gets noisy when one panel is still waiting for an answer and somebody starts feeding information from another panel.

That is how a real color from one module ends up beside a real number from a different module.

When a panel is active, I keep its name attached to the conversation until Blind confirms what happened.

A Cable call might need several pieces before Mute can answer.

Direction needs a different set.

Calculator changes state halfway through.

Piano may need an ordered sequence.

Those procedures are not interchangeable, so I do not force every module into one giant universal callout format. The only shared habit is that the current panel stays identifiable until the action is finished.

If I have reliable state and simply need the next module action, that is when the <Link href="/bombanana/module-solver">BOMBANANA Module Solver</Link> becomes useful.

<h2 id="swap-roles" className="scroll-mt-24">
  I swap the seat that keeps producing the same kind of mistake
</h2>

One explosion does not make me rotate all three roles.

Repeated failure in the same place does.

If Mute consistently reaches the right rule but nobody can read the returned gesture, I try somebody else on the manual.

If Deaf repeatedly combines one stage's value with another stage's color, I put the strongest information manager in the middle.

If Blind receives clean physical instructions but still makes accidental inputs or cannot report Braille while operating the case, another player may be a better bomb operator.

Some failures have nothing to do with the person sitting there.

Changing Blind does not fix two different definitions of left.

Changing Mute does not fix a team where “repeat” and “reset” mean the same thing.

Those are shared-protocol problems. I repair the convention before moving the players.

A single rotation can still be useful because everybody gets to see what the other two seats are actually handling. After that, I settle on the lineup that drops the least information.

<h2 id="failed-run" className="scroll-mt-24">
  After a strike or explosion, I reconstruct the last bad action
</h2>

“Who messed up?” rarely gives us anything useful for the next attempt.

I start from the physical input that failed and walk backward.

1. **What did Blind actually touch, cut, move, or enter?**
2. **What instruction did Blind think they received?**
3. **What did Deaf read from Mute?**
4. **Which state did Deaf originally bring to Mute?**
5. **Was Blind's information complete when that state started?**
6. **Did the panel change before the final action happened?**

That sequence separates failures that otherwise look identical.

A Cable miss can begin with a missing wire count.

A Direction miss can come from perspective.

A Calculator mistake can use a correct value from the wrong stage.

An ordered panel can lose one item while every other item remains correct.

Repeating the exact same level without identifying which of those happened usually reproduces the same problem under a fresh timer.

Once the broken point is clear, the next attempt gets one concrete change:

- name the module before the numbers;
- attach position to the value;
- lower the manual before gesturing;
- reset after the state advances;
- keep Blind's hands off while the answer is disputed.

<h2 id="replay" className="scroll-mt-24">
  Passing the level by accident is not the same as fixing the communication
</h2>

Sometimes the bomb is defused and nobody can explain why the last input worked.

I do not treat that as a clean solve.

If a guess saved the run, if two players still disagree about what a gesture meant, or if the correct input happened before the team understood the call, I am happy to replay the same level once.

The target on the replay is not a faster timer.

It is a cleaner exchange.

I want Blind to know exactly what to touch, Deaf to know what every number belongs to, and Mute to be able to return the answer without inventing a new gesture halfway through.

When we can do that and the same mistake is no longer appearing, I move on.

If the question is where Campaign gets harder or whether the next level adds too much on top of a shaky process, I check the <Link href="/bombanana/levels">BOMBANANA Levels & Walkthrough</Link> before pushing forward.

<h2 id="before-start" className="scroll-mt-24">
  Five agreements are enough to start a serious run
</h2>

Before several modules begin competing for attention, our team locks in five things:

1. **Left and right use one perspective.**
2. **Physical positions are counted in one direction.**
3. **Yes and no are visually unmistakable.**
4. **Repeat one field and reset the state are different commands.**
5. **Blind waits while an answer is incomplete or disputed.**

That is enough structure.

Nobody needs every module memorized. The information simply has to survive the trip from the bomb to the manual and back without changing meaning.

Once that part is reliable, a remaining failure is much easier to classify: either the module itself needs solving, or the team needs more practice with that specific stage of Campaign.

<h2
  id="two-clues"
  className="scroll-mt-24"
>
  28 Piano states collapse to one row and one color
</h2>

Piano looks information-heavy because the manual contains **7 Braille rows**, **4 light colors**, and **28 possible note sequences**.

During the bomb, I only need two pieces of that table:

**Which Braille number is showing?**

and:

**Which light is active?**

Those two clues select exactly one sequence.

That is the point where I want the lookup finished before the keyboard conversation begins.

<h2
  id="where-teams-get-stuck"
  className="scroll-mt-24"
>
  The first Piano wall is usually too much information, not too little
</h2>

One early attempt became much harder than the rule itself.

Instead of reducing the panel to:

**number + light → four notes**

the call expanded into individual key labels, octave labels, several Braille values, the LED color, and questions about which player was supposed to pass which part.

At one point the team was calling keys such as:

**C7, D7, E7, F7, G7, A7, B7**

while still trying to establish which Braille information actually mattered.

That creates a bad order of operations.

Seven key names are already more information than the lookup needs to begin.

The manual first needs a **single Braille row and a single light color**.

Only after that lookup returns four notes do those note names become actionable.

When Piano is taking half a minute before anyone has even chosen the table cell, this is the first thing I simplify.


<h2
  id="keep-the-sequence"
  className="scroll-mt-24"
>
  Four notes are short enough to relay once, but long enough to lose one
</h2>

Cable can come back as one position.

Direction can come back as one button.

Piano returns **four ordered inputs**.

That changes the communication problem.

If the answer is:

**C → E → G → C**

then hearing:

**C, E, G**

correctly is still a failed handoff if the final C disappears.

I keep the four notes as one packet.

A practical call sounds like:

**“Piano. One Yellow. C, E, G, C.”**

The player on the keys repeats:

**“C, E, G, C.”**

Then the input starts.

Breaking the sequence into unrelated note guesses makes it harder to know whether the second E, repeated C, or another similar note belongs to the current answer or a previous question.


<h2
  id="color-and-braille"
  className="scroll-mt-24"
>
  Missing either clue sends the manual reader to the wrong sequence
</h2>

The light is not decoration.

The Braille number is not enough by itself.

For Braille **1**, the four colors already produce four different answers:

- Red selects one sequence
- Yellow selects another
- Green selects another
- Blue selects another

The table owns the exact notes, so I do not duplicate all four rows again here.

The practical consequence is more important: if somebody says only:

**“Piano, one.”**

I wait for the light.

Likewise:

**“Piano, Yellow.”**

still leaves seven possible rows.

This became a real source of delay in an early run. The light had to be called again, then the team realized the Braille value also had to reach the manual reader before the notes could be settled.

Two small clues sent together are faster than repeatedly repairing one incomplete clue.


<h2
  id="after-confusion"
  className="scroll-mt-24"
>
  If the note chain gets muddy, rebuild the lookup before touching another key
</h2>

Suppose the team reaches:

**“Was that E or F?”**

or:

**“Did we already press the third note?”**

At that point, another isolated note does not repair the shared state.

I go back to:

**Braille number → active light → full four-note answer**

and repeat the sequence from the communication side before continuing.

The same applies when two players disagree about the light.

A remembered note sequence is not strong enough evidence to choose between them because one different color can move the lookup into another column.

If the table lookup is clear but the four-note answer repeatedly disappears between Mute, Deaf, and Blind, the bottleneck belongs to the <Link href="/bombanana/roles">BOMBANANA Roles Guide</Link>, not another Piano rule.


<h2
  id="level-nine"
  className="scroll-mt-24"
>
  Level 9 tells me whether Piano is ready for a busier bomb
</h2>

Piano first becomes a fixed Campaign module on **Level 9**.

That bomb gives **3:30** and contains:

**Random Easy + Piano**

with:

**Pressure**

Level 10 raises the coordination cost:

**Symbol + Piano**

with:

**Alarm**

and gives **4:00**.

The extra thirty seconds does not automatically make Level 10 the better practice room. It also adds another medium module and changes the Chaos pressure.

Level 9 is where I want the Piano procedure to become stable.

I replay it when any of these keeps happening:

- the Braille number arrives without the light;
- the light has to be asked for several times;
- the manual reader starts listing keyboard labels before selecting the table cell;
- one of the four notes regularly disappears from the relay;
- the team knows the right four notes but cannot agree which note has already been pressed.

One messy attempt is not enough to send me backward.

When the **same Piano failure** survives several attempts, moving into Symbol + Piano + Alarm only gives that failure more places to hide.

Once `number + color` reliably becomes one four-note packet, I push on.

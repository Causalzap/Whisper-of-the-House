<h2 id="what-the-game-tests" className="scroll-mt-24">
  The Bomb Is Only Half of What the Team Is Solving
</h2>

The opening levels can make BOMBANANA look like a stack of small logic puzzles.

That impression does not survive for long.

Blind handles the bomb.

Mute has the manual.

Deaf sits between them.

Those restrictions mean a team can understand the puzzle rule perfectly and still lose because the useful answer never arrives intact.

A Cable lookup may return the correct color, while Blind needs a physical position.

A Direction answer may be correct, while two players mean opposite things by “left.”

A longer module can survive the lookup and then fail because the second or third value disappears during the relay.

So before learning another rule, I ask a more useful question:

**Where did the information stop being useful?**

That question is the fastest way I know to separate a puzzle problem from a communication problem.


<h2 id="diagnose-the-failure" className="scroll-mt-24">
  Four Failures Can Look Like the Same Bad Run
</h2>

### I do not understand the rule

The panel is visible, but I still do not know which information matters.

That needs the module guide.

For the modules with mature dedicated pages:

- <Link href="/bombanana/wire">Cable / Wire</Link>
- <Link href="/bombanana/direction">Direction</Link>
- <Link href="/bombanana/calculator">Calculator</Link>
- <Link href="/bombanana/symbol">Symbol</Link>
- <Link href="/bombanana/piano">Piano</Link>
- <Link href="/bombanana/soundboard">Soundboard</Link>
- <Link href="/bombanana/switch">Switch</Link>

### I know the rule but cannot make the physical input

Cable is the cleanest example.

Knowing the target color is not the same as telling Blind which cable to cut.

This is a translation problem, not another table lookup.

### The module changed and we kept using the old answer

Some panels have stages or changing states.

A correct input can make the previous answer stale immediately.

When that happens, I read what the panel shows **now** instead of defending what was correct five seconds ago.

### Everybody knows the answer and we still fail

At that point I stop blaming the puzzle.

If the right information repeatedly disappears between Mute, Deaf, and Blind, the problem belongs in the <Link href="/bombanana/roles">Roles & Communication Guide</Link>.

<h2 id="solver-or-guide" className="scroll-mt-24">
  A Solver Helps Only After the Inputs Are Trustworthy
</h2>

There is a big difference between:

**“I don't understand this panel.”**

and:

**“I have three cables, a Green light, and these three colors. Which position do I cut?”**

The second problem is ready for a solver.

The current <Link href="/bombanana/module-solver">BOMBANANA Module Solver</Link> handles:

**Cable / Wire**

**Direction**

and:

**Calculator**

For those modules, the fastest path during a live bomb is:

**read the required state → enter it → take the answer → act → look at the panel again**

I do not use the solver as a substitute for understanding which fields belong to the current module.

Bad input produces a very fast bad answer.


<h2 id="campaign-learning-curve" className="scroll-mt-24">
  The 30-Level Campaign Changes What the Team Has to Be Good At
</h2>

The Campaign is more useful as a training curve than as thirty separate bombs to memorize.

I think about it in five stretches.

### Levels 1–7: build a usable language

The early game teaches short state packets and basic relay discipline.

This is where Cable, Direction, Calculator, and the easier module pool expose whether the team can finish one conversation before starting another.

I would rather fix bad left/right language here than carry it into a level with several other problems active.

### Levels 8–15: descriptions and sequences get longer

Symbol, Piano, and Soundboard change the amount of information being moved.

A vague description that only wastes two seconds on an early Cable can become much more expensive when the team is holding a stage, color, Braille value, sound target, or note sequence.

The dedicated <Link href="/bombanana/symbol">Symbol</Link>, <Link href="/bombanana/piano">Piano</Link>, and <Link href="/bombanana/soundboard">Soundboard</Link> guides own those procedures.

### Levels 16–20: state integrity becomes the wall

Switch enters as a fixed Campaign problem at Level 16.

This is where partial information becomes especially dangerous because several ordered values belong to one solve.

Maze also enters this part of the Campaign.

If Level 16 already turns one Switch state into three rereads, I fix that before trying to learn the same communication habit under a busier bomb.

### Levels 21–24: late modules arrive before the random-hard stretch

Morse first becomes a fixed Campaign problem at **Level 21**.

Monkey-Says follows at **Level 23**.

If either one is the reason the team cannot advance, I use its first fixed appearance as the practice point instead of hoping a later random combination will be easier.

### Levels 25–30: procedure matters more than memorizing a layout

The final stretch leans heavily on **Random Hard** slots.

By this point the question is no longer whether I remember one exact Level 27 bomb.

It is whether the team's procedures still work when the module mix changes.

The exact timers, module compositions, first fixed appearances, mistake limits, and all thirty Campaign setups stay in the <Link href="/bombanana/levels">Levels & Walkthrough</Link>.


<h2 id="when-to-retry" className="scroll-mt-24">
  One Explosion Is Noise; the Same Failure Twice Is a Pattern
</h2>

I do not restart my whole approach after every bad run.

A misclick is a misclick.

A single missed warning can happen.

A player can simply forget one value.

The useful signal is repetition.

If the same module causes the same failure twice, I stop feeding attempts into the next level.

That might be:

- Cable repeatedly reaching Blind as a color instead of a position;
- Direction repeatedly producing “your left or my left?”;
- Calculator repeatedly confusing the raw result with the final key;
- Soundboard repeatedly starting with all nine buttons instead of finding the sound first;
- Switch repeatedly losing part of its full state;
- a solved answer repeatedly disappearing somewhere in the role relay.

At that point another immediate retry is usually just another chance to reproduce the same mistake.

I change one thing first.


<h2 id="module-decisions" className="scroll-mt-24">
  Different Modules Reward Different Kinds of Discipline
</h2>

The fastest improvement comes from stopping the assumption that every panel wants the same style of callout.

### Cable turns a lookup into a physical instruction

The manual can identify a color.

Blind needs a position.

The <Link href="/bombanana/wire">Cable / Wire Guide</Link> owns the full count, LED, target-color, and physical-position flow.

### Direction combines a small rule with a perspective problem

The exact answer comes from the light and Braille state.

The expensive mistake is often what happens after the answer is known.

The <Link href="/bombanana/direction">Direction Guide</Link> owns the full mapping; the broader perspective convention belongs with Roles.

### Calculator changes jobs halfway through

It starts as arithmetic.

After the raw result is entered, it becomes a second lookup.

That state change is why the <Link href="/bombanana/calculator">Calculator Guide</Link> keeps the complete worked examples and final-key logic in one place.

### Symbol, Piano, and Soundboard are not just “more difficult tables”

They create longer chains.

Symbol cares about the sounding shape and current stage.

Piano holds an octave, active light, and note sequence.

Soundboard first searches for the sounding button, then turns its state into a 3×3 input pattern.

Trying to describe everything visible at once makes all three harder than they need to be.

### Switch punishes incomplete state

Switch is different again.

Its useful input is a complete ordered state rather than one color or one number arriving in isolation.

The <Link href="/bombanana/switch">Switch Guide</Link> is where I keep that full read → resolve → confirm → Enter process.


<h2 id="chaos-priority" className="scroll-mt-24">
  Chaos Changes the Meaning of “What Should We Solve Next?”
</h2>

A normal defusal module has an answer.

Chaos creates an ongoing demand for attention.

That is why I do not force one universal module order onto every bomb.

A familiar panel that can be finished immediately may be worth clearing.

A Chaos control already moving toward danger can override that plan.

The practical question becomes:

**What action keeps the run alive without destroying the state we were already solving?**

I stabilize urgent danger first, then return to a confirmed current state on the interrupted module.

The full Campaign ramp from one Chaos control to stacked Alarm, Pressure, and Slider pressure belongs in the <Link href="/bombanana/chaos">Chaos Guide</Link>.


<h2 id="buy-or-skip" className="scroll-mt-24">
  The Three-Person Group Matters More Than the Puzzle List
</h2>

I would buy BOMBANANA when I already have **three people** who enjoy getting better at communication together.

The strongest part of the game is the improvement curve:

a call that takes thirty confused seconds becomes a short packet;

a shape that had three different names gets one stable name;

a failed relay turns into a repeatable convention;

a role swap suddenly makes the whole group faster.

That is the fun loop.

I would hesitate when getting three people together is already going to be the hardest part of every session.

The core design expects Blind, Deaf, and Mute to hold different pieces of the solution.

If my group mainly wants puzzles where one person can understand the answer and simply read it aloud, BOMBANANA's restrictions may feel like friction rather than the point of the game.

So my purchase decision is less:

**“Do these individual puzzles look clever?”**

and more:

**“Will these three people enjoy solving communication mistakes together?”**


<h2 id="roles-and-swapping" className="scroll-mt-24">
  A Bad Role Fit Can Look Like a Hard Module
</h2>

Sometimes the puzzle is not getting harder.

The wrong player is simply doing the wrong job.

If Mute consistently finds the correct manual answer but cannot compress it into something Deaf can relay, another hour of memorizing the table may not fix the run.

If Deaf keeps losing ordered states, longer modules will magnify that weakness.

If Blind understands every instruction but hesitates because physical positions are vague, the group needs cleaner action language.

I consider a role swap when the same type of failure survives across several different modules.

That tells me the bottleneck probably belongs to the player-role fit rather than one rule.

The full Blind / Deaf / Mute workflow, gesture conventions, physical-position language, and swap decisions are in the <Link href="/bombanana/roles">Roles Guide</Link>.


<h2 id="modes" className="scroll-mt-24">
  Campaign First, Then Choose Endless or Custom for a Reason
</h2>

The full release includes:

**Campaign**

**Endless**

and:

**Custom**

Campaign is where I start.

Its progression gives the team a chance to discover one weakness at a time before the harder module pools and heavier Chaos combinations arrive.

Endless makes more sense once the basic procedures already work.

At that point I am testing how long the team can preserve those procedures while pressure keeps accumulating.

Custom serves a different purpose.

I use it when I want more control over the kind of run the group is practicing rather than treating the next Campaign clear as the only useful result.

The mode choice becomes simple:

**still learning how modules work → Campaign**

**testing sustained execution → Endless**

**practicing or experimenting with a chosen setup → Custom**


<h2 id="late-game-bottlenecks" className="scroll-mt-24">
  Maze, Morse, and Monkey-Says Are Better Practiced Before the Final Six Levels
</h2>

Not every later module needs to become a separate study project immediately.

The Campaign already gives useful checkpoints.

**Maze** first gets a fixed slot at **Level 18**.

**Morse** first gets a fixed slot at **Level 21**.

**Monkey-Says** first gets a fixed slot at **Level 23**.

If one of those modules is eating most of the timer, I would rather practice around its first fixed appearance than wait for Levels 25–30, where Random Hard slots make the surrounding bomb less predictable.

That gives me a cleaner diagnosis:

**Is this specific module still the problem, or does the team fall apart only after several hard states are active at once?**

Those are different problems, and they need different fixes.

The current Steam achievement set has **23 achievements**.

A player going for full completion has different priorities from a group still learning Campaign modules.

The cleanup includes Campaign milestones, Endless targets, repeated actions, hidden achievements, and several goals that are much faster when grouped into the same session.

<h2 id="session-stop" className="scroll-mt-24">
  I Stop the Session When the Retry Has No New Information
</h2>

There is a useful difference between frustration and diagnosis.

If the team can say:

**“We pressed before confirming the fourth Switch.”**

that is actionable.

If the answer is:

**“I thought you meant the other one.”**

I need to know which part of the relay made “the other one” possible.

If everyone is still arguing about what happened, immediately starting the next attempt usually adds another explosion without adding a lesson.

I make one convention concrete first.

For example:

**everything is counted left to right**

or:

**Direction always uses Blind's perspective**

or:

**“again” means repeat the last value, while “reset call” means read the whole state again**

Then I retry.

The next run should contain at least one deliberate change.


<h2 id="ktane" className="scroll-mt-24">
  Is BOMBANANA Like Keep Talking and Nobody Explodes?
</h2>

They sit in the same broad family of co-op bomb-defusal games where information is split between the person interacting with the bomb and the people working from instructions.

BOMBANANA's defining twist is the **three-role chain**.

Blind, Deaf, and Mute do not simply share one open voice channel with equal access to the same information.

The answer often has to be transformed as it moves between players.

That makes the communication restriction itself part of the puzzle rather than just the way the manual is delivered.


<h2 id="what-to-learn" className="scroll-mt-24">
  I Would Memorize the Input Packet Before Memorizing the Answer Table
</h2>

The manual contains a lot of possible answers.

Most runs use only a small fraction of them.

The more reusable skill is knowing what each panel needs before anybody begins speaking.

If I can identify:

**which module this is**

**which state matters**

**which player can see or hear that state**

**what form the final instruction must take**

then the manual and solver can do their jobs quickly.

If those four pieces are still unclear, memorizing another row of answers usually does not fix the real bottleneck.

That is the overall rule I carry through BOMBANANA:

**understand the state, preserve it through the relay, then make one confirmed action.**

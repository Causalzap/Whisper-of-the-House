<h2 id="diagnose-first" className="scroll-mt-24">
  The last ten seconds of the run usually tell me more than the explosion
</h2>

A failed bomb can feel like one big mistake.

I get better results by separating it into four different kinds of failure.

**Rule failure:** I can see the panel, but I still do not know which information matters or how the manual turns it into an answer.

**State failure:** the rule is understood, but one color, number, stage, position, or other live value was read incorrectly or became stale.

**Relay failure:** the answer was right at some point, then changed meaning or lost a position while moving between players.

**Attention failure:** the team knew what it was doing, but another module, Chaos hazard, or unfinished state consumed the attention needed to execute it.

Those four failures can end with the same explosion.

They do not need the same fix.

A second manual lookup helps the first one.

A clean reread helps the second.

The third belongs in <Link href="/bombanana/roles">Roles & Communication</Link>.

The fourth is usually a question of priority, interruption, or Campaign readiness rather than another rule table.

<h2 id="manual-live" className="scroll-mt-24">
  The BOMBANANA manual gets faster once the panel has a name
</h2>

When Mute opens the manual, I do not want the whole bomb described at once.

The first useful fact is the module.

“Three cables” immediately narrows the problem.

“A light, some colors, something with numbers, and another thing flashing” does not.

Once the module is identified, the next question is equally concrete:

**What state does this module need right now?**

That is the point where the manual becomes useful instead of overwhelming.

Cable needs one kind of state.

Direction needs another.

Calculator changes state during the solve.

Switch holds several values at once.

Morse separates the active position from the code that belongs there.

The manual is therefore less like a book I read from front to back and more like a set of doors. I only need to open the one that matches the panel in front of us.


<h2 id="module-route" className="scroll-mt-24">

</h2>

For **Cable / Wire**, the full count, light, color, target, and physical cut flow is in the <Link href="/bombanana/wire">Cable / Wire Guide</Link>.

For **Direction**, the light-and-Braille mapping stays in the <Link href="/bombanana/direction">Direction Guide</Link>.

For **Calculator**, the arithmetic stage and the later LED decision stay together in the <Link href="/bombanana/calculator">Calculator Guide & Solver</Link>.

If the panel is **Symbol**, I use the <Link href="/bombanana/symbol">Symbol Guide</Link>. For **Piano**, the note sequence and octave work stay in the <Link href="/bombanana/piano">Piano Guide</Link>. For **Soundboard**, I use the <Link href="/bombanana/soundboard">Soundboard Guide</Link>.

A **Switch** run is safest when its full ordered state survives until Enter; the actual conditions and recovery cases are in the <Link href="/bombanana/switch">Switch Guide</Link>.

For **Morse**, I identify the active slot, decode the complete signal, and keep the digit attached to that position. The full number table, reread logic, and Enter decision are in the <Link href="/bombanana/morse">Morse Code Guide</Link>.

That leaves this page free to answer a broader question:

**Which kind of help does the current run actually need?**


<h2 id="solver-or-manual" className="scroll-mt-24">
  A solver is quickest when nobody is arguing about the input
</h2>

The <Link href="/bombanana/module-solver">BOMBANANA Module Solver</Link> currently handles:

**Cable / Wire, Direction, and Calculator.**

I use it when the panel has already been identified and the current values are trustworthy.

A state such as:

**three cables + current light + colors in order**

is ready to become an action.

A state such as:

**“I think it was Green, unless that was the other panel”**

is not improved by faster calculation.

The solver can remove lookup time.

It cannot decide which half-remembered state actually belongs to the bomb.

Whenever the returned answer seems impossible, the fastest check is usually the panel itself.


<h2 id="three-roles" className="scroll-mt-24">
  Blind, Deaf, and Mute can each be correct while the team is still wrong
</h2>

Blind works on the bomb.

Mute has the manual.

Deaf is part of the path between them.

That split is what makes BOMBANANA different from a normal puzzle game with three people sitting in voice chat.

The answer often has to change form while it travels.

A manual result may be a color, while Blind needs a physical position.

A direction may be correct in the manual and wrong when two players use different viewpoints.

A sequence may begin accurately and lose one item before the last player acts.

When that kind of failure appears across several unrelated modules, memorizing more module rules is poor practice. I change the relay or the role fit instead.

The <Link href="/bombanana/roles">Roles & Communication Guide</Link> covers the Blind / Deaf / Mute workflow, gesture and position conventions, what happens when the manual blocks visual communication, and when a role swap is worth trying.


<h2 id="campaign" className="scroll-mt-24">
  The 30-level Campaign tells me when a weakness has started following us forward
</h2>

BOMBANANA's Campaign contains **30 levels**.

I use those levels as a progression route rather than thirty scripts to memorize.

Early bombs give the team room to establish basic module language.

Later stages add larger states, longer sequences, random difficulty pools, and more simultaneous pressure.

That means a clear can be misleading.

If a new module only worked because one player guessed correctly at the end, the level number advanced but the skill did not.

If the same module fails for a different reason on the next attempt, that may simply be learning.

If the identical mistake survives three runs, I have enough evidence to stop pushing.

The exact timers, compositions, first module appearances, mistake allowances, and replay checkpoints are in the <Link href="/bombanana/levels">BOMBANANA Levels & Walkthrough</Link>.


<h2 id="chaos" className="scroll-mt-24">
  Chaos is the moment when “solve the next module” stops being a complete plan
</h2>

Defusal modules eventually clear.

Chaos keeps demanding attention while the rest of the bomb is still alive.

That changes the question from:

**“Which puzzle should we solve?”**

to:

**“What needs attention now, and what unfinished information will still be trustworthy afterward?”**

I keep the detailed Slider, Pressure, Alarm, interruption, and recovery decisions in the <Link href="/bombanana/chaos">Chaos Guide</Link>.

On the Hub, the important rule is simpler: when a known module suddenly becomes difficult only because the team cannot stay on it long enough to finish, I diagnose the interruption before relearning the module.


<h2 id="smaller-modules" className="scroll-mt-24">
  Color Slider, Maze, and Monkey-Says expose three different weak habits
</h2>

Some modules are useful to understand here without turning them into another long lookup route.

### Color Slider

Color Slider appears early enough that I use it as a check on positional language.

Several colored controls need Up or Down decisions.

The dangerous habit is letting the order drift while the answer is being returned.

If the first color was called from the left, the rest of the row stays in that same physical order until the module is done.

A team that keeps reversing, skipping, or renumbering those positions is likely to feel the same weakness much harder later when Switch carries a larger state.


### Maze

Maze becomes much easier once nobody moves immediately.

Before the first direction, I want three things settled:

**which maze is active, where the red start is, and where the green destination is.**

The route can be perfectly correct for the wrong starting coordinate.

That is why I would rather spend a few seconds fixing the coordinate convention before the first move than spend the next minute trying to understand why a sensible path hit a wall.

If a movement goes wrong and nobody can identify the current square anymore, recovering the position matters more than continuing the memorized route.


### Monkey-Says

Monkey-Says asks for a different kind of memory.

Later decisions can depend on information carried forward from earlier inputs, so the current highlight is not always the whole state.

The useful habit is keeping the accumulated sequence somewhere stable instead of asking three people to remember different fragments of it.

When a stage fails, I want to know whether the new input was wrong or whether an earlier item disappeared from the chain.

Those are different repairs.


<h2 id="retry-decision" className="scroll-mt-24">
  I replay for a repeated cause, not simply because the bomb exploded
</h2>

One misclick does not make me move backward.

Neither does one awkward random combination.

A useful replay starts when the failure has become predictable.

Cable reaches Blind without a usable position again.

Direction produces another “your left or my left?”

Calculator reaches the second state and the team still uses the first answer.

Switch arrives at Enter with one value disputed.

Morse reaches four digits but one of them no longer has a trusted slot.

Those are not five different reasons to be frustrated.

They are five pieces of evidence.

Once the cause is visible, I change one part of the process before the next attempt.

If the team cannot say what will be different on the retry, starting the timer again rarely teaches us much.


<h2 id="modes" className="scroll-mt-24">
  Campaign, Endless, and Custom are useful for different kinds of sessions
</h2>

The full game gives me three main ways to play:

**Campaign**

**Endless**

**Custom**

Campaign is where I learn the game because its progression gives new problems somewhere to enter.

Endless makes more sense after the basic procedures already survive normal Campaign pressure. The question there is how long the team can keep those procedures intact.

Custom is the mode I choose when the session has a specific purpose.

If Switch is the problem, I would rather create repetitions around that weakness than wait for a random late-game bomb to produce a useful practice opportunity.

If we are testing a new role assignment, Custom can also remove unrelated difficulty while we find out whether the swap actually helps.

Campaign answers **“what should we learn next?”**

Endless asks **“how long can we sustain it?”**

Custom asks **“what exactly do we want to test?”**


<h2 id="buy-or-skip" className="scroll-mt-24">
  The best reason to buy BOMBANANA is the group, not the number of puzzle types
</h2>

I would choose BOMBANANA for a group of **three people** who enjoy improving together.

The memorable part is not just discovering another module.

It is hearing a terrible thirty-second explanation shrink into five clean seconds after a few attempts.

It is finding one name for a shape everybody previously described differently.

It is realizing a player who struggled as Mute becomes much better when the roles rotate.

That improvement loop is the game.

I would hesitate if reliably assembling three players is already difficult, or if the group mainly wants cooperative puzzles where one person can understand the solution and simply read it aloud.

BOMBANANA deliberately gets in the way of that easy information flow.

For the right group, that friction creates the game.

For the wrong group, it is simply friction.


<h2 id="completion" className="scroll-mt-24">
  Level 30 is the end of Campaign, not the end of every goal
</h2>

The achievement set contains **23 achievements**.

Finishing Campaign and finishing everything therefore lead to different sessions.

Once the group is no longer trying to learn the next Campaign module, completion work can shift toward Endless targets, repeated actions, hidden requirements, and cleanup that is more efficient when several goals are combined.

I keep that route in the <Link href="/bombanana/achievements">BOMBANANA Achievements Guide</Link> so achievement cleanup does not get mixed into the main Campaign decisions.


<h2 id="ktane" className="scroll-mt-24">
  BOMBANANA feels familiar to Keep Talking players, but the information path is harsher
</h2>

BOMBANANA and Keep Talking and Nobody Explodes belong to the same broad family: one side interacts with a bomb while instructions live somewhere else.

The difference I feel immediately is the three-role split.

Blind, Deaf, and Mute do not have equal access to one shared conversation.

Useful information may have to cross more than one player, and the form that leaves the manual is not always the form Blind needs at the bomb.

That extra transformation is why communication mistakes become a real game system rather than background noise.


<h2 id="what-to-fix-next" className="scroll-mt-24">
  The next improvement is usually visible before the next module is
</h2>

After a run, I care less about the final explosion than the last piece of information that was still trustworthy.

If the rule was unknown, I learn the module.

If the state was wrong, I change the read.

If the answer was right but unusable, I change the relay.

If several correct procedures collapsed only when the bomb became crowded, I work on priority and interruption.

That gives every retry a reason.

BOMBANANA becomes much easier to navigate once I stop treating every loss as a request for another answer table and start asking what kind of failure the team actually produced.

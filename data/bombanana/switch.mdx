  A BOMBANANA Switch board gives me **four light colors and four numbers**. I keep both rows in the same left-to-right order until all four switch positions are known.

  **Colors first. Numbers second. Four Up/Down answers third. Enter last.**

  If one color, number, or physical position becomes uncertain before Enter, I stop and rebuild the board instead of guessing the missing slot.

<h2 id="whole-state" className="scroll-mt-24">
  Our first clean Switch solve came after two very different failures
</h2>

Switch did not become easier for us because somebody suddenly memorized the manual.

The improvement came from changing how we handled the board.

On an early attempt, Blind was still working out how to interact with the module while the other two players were already trying to communicate switch directions. The rule answer was arriving before the physical side was ready to use it.

The next attempt got further.

We had the four colors.

We knew the switches moved Up or Down.

Then one player signaled:

**“Two.”**

The receiver saw the number, saw a downward motion, and read the combination as:

**second switch → Down**

That was not what the sender meant.

The run ended, and only afterward did the team realize that “two” had been part of a question about which color occupied the second position.

On the next retry, the wording changed.

Instead of throwing a position into the air and hoping everybody attached it correctly, the call became:

**“The first one is Red.”**

Then the action.

**“The second one is Blue.”**

Then the action.

**“The third one is Green.”**

Then the action.

The fourth position followed the same way.

That run finished with roughly **one minute still on the clock**.

The logic table had not changed.

The board finally stayed understandable from the first call to the last switch.

<h2 id="order-matters" className="scroll-mt-24">
  I freeze the board as four positions before anybody starts solving it
</h2>

The Switch panel is easiest for me to hold as four paired slots.

For example:

**Position 1 — Red — 9**

**Position 2 — Green — 3**

**Position 3 — Blue — 7**

**Position 4 — Yellow — 6**

That is much safer than remembering:

**Red, Green, Blue, Yellow**

and separately:

**9, 3, 7, 6**

with no physical positions attached.

A real Switch read used exactly that color order and number string:

**Red / Green / Blue / Yellow**

**9 / 3 / 7 / 6**

The important part is not memorizing `9376`.

The useful part is preserving:

**Red = 9**

**Green = 3**

**Blue = 7**

**Yellow = 6**

in their actual left-to-right slots.

The same four colors in another order are another board.

These are not interchangeable:

**Red / Yellow / Blue / Green**

and:

**Green / Blue / Yellow / Red**

Every color is present in both examples.

Their physical positions are different.

So “we have Red, Yellow, Blue, and Green” is not yet a usable Switch read.


<h2 id="numbers-change-answer" className="scroll-mt-24">
  Familiar colors do not make the previous Up/Down pattern reusable
</h2>

The number row is not decoration.

Several completed Switch boards can share exactly the same color order and still finish with different switch positions.

All three begin with:

but the outputs are different.

**Down / Down / Up / Down**

For:

**7 / 9 / 3 / 6**

**Up / Up / Down / Down**

For:

**1 / 4 / 3 / 6**

it becomes:

**Down / Up / Down / Down**

That kills one tempting shortcut.

Seeing the same familiar color order does not give me permission to reuse the pattern from the previous bomb.

The current numbers decide the current board.


<h2 id="read-packet" className="scroll-mt-24">
  Eight values sound slower than four partial guesses; in practice they save the retry
</h2>

Switch asks the team to hold more information at once than many of the early modules.

There are four colors.

There are four numbers.

Before anyone on the manual side starts turning those into four physical positions, I want the complete read.

A clean call sounds like this:

**“Switch.”**

**“Colors: Red, Green, Blue, Yellow.”**

**“Numbers: Nine, Three, Seven, Six.”**

Then the bomb side stops adding unrelated information for a moment.

That small pause matters.

If somebody begins describing Cable while the second Switch number is still being checked, the next number can be perfectly accurate and still land in the wrong conversation.

Switch rewards a slightly slower read at the beginning because execution becomes much faster once the whole row is settled.

A broken board is the opposite.

One color gets repeated.

The second number is challenged.

Somebody starts solving position one while position four has not even arrived.

By the time the final switch answer comes back, nobody is completely certain that all eight source values still belong to the same read.


<h2 id="set-switches" className="scroll-mt-24">
  Enter is the fifth action, never the first four compressed into one guess
</h2>

Once the manual side has finished, the answer still has to survive the trip back to the physical switches.

I keep that row boring:

**first**

**second**

**third**

**fourth**

always from left to right.

A returned answer may be:

**Down / Down / Up / Down**

Blind can now work straight across the module:

First goes Down.

Second goes Down.

Third goes Up.

Fourth goes Down.

Only then does Enter matter.

I do not treat Enter as part of the solve while one switch is still being debated.

If the current situation is:

**Down / Down / ? / Down**

then the board is not “almost submitted.”

It has one unresolved position.

That position gets resolved before the team talks about Enter.

One uncertain switch can turn three correct decisions into one failed submission.


<h2 id="when-to-reread" className="scroll-mt-24">
  I throw away the read when I can no longer point to where the uncertainty started
</h2>

Not every hesitation requires all eight values again.

If somebody clearly missed only the fourth color and the first three are still agreed on, repeating the fourth color is fine.

The reset becomes necessary when the uncertainty has spread.

### The color order broke halfway through

If the call started:

**Red, Green...**

then somebody interrupts and nobody agrees whether Blue or Yellow came next, I restart the four colors from the left.

Trying to repair positions three and four while positions one and two live only in memory creates a board nobody can audit.

### One number may belong to the wrong slot

Suppose somebody remembers `9 / 3 / 7 / 6`, but another player thinks the middle pair was `7 / 3`.

I reread all four numbers.

The problem is no longer “what was the third number?”

The problem is whether the number-to-position mapping is intact.

### The four Up/Down answers lost their positions

Hands come off the switches.

The return starts again from:

**first**

**second**

**third**

**fourth**

No one keeps flipping controls while the order is still being reconstructed.

### Enter was pressed and the module did not clear

The old pattern loses its authority.

I look at the module again before repeating anything.

The next useful move comes from what the panel shows now, not from the answer we wish had worked.


<h2 id="real-wall" className="scroll-mt-24">
  Switch usually breaks before the logic table does
</h2>

Eight visible values make the module look like a difficult rule puzzle.

The actual failures are often much more ordinary.

A number gets attached to the wrong light.

A player gives the fourth value while another player is still asking about the second.

Blind begins moving switches before the answer row is complete.

A familiar color order makes somebody remember yesterday's Up/Down pattern.

Enter gets pressed because three positions feel certain and the fourth feels “probably right.”

None of those problems require a more complicated rule explanation.

They require the current board to survive long enough to produce one clean four-switch answer.

That is why the fastest teams do not necessarily sound fastest during the first call.

The source read is deliberate.

The physical execution becomes fast afterward.


<h2 id="two-resets" className="scroll-mt-24">
  “Say that one again” and “start the board again” are not the same request
</h2>

There is a useful difference between losing one item and losing confidence in the board.

If the call was:

**Red, Yellow, Blue, Green**

and I heard the first three perfectly but missed Green, I ask for the last color again.

Nothing else has become uncertain.

Now imagine this exchange:

“Was the second number three?”

“No, I thought three was third.”

“Was Blue second or third?”

At that point, another isolated answer makes the board harder to trust.

I want the full read again.

The difference is easy to recognize:

**one missing fact**  
→ repeat that fact

**uncertain positions or conflicting memories**  
→ restart the board

If this same distinction keeps breaking across several different modules—not only Switch—I use the <Link href="/bombanana/roles">BOMBANANA Roles & Communication Guide</Link> to settle the team's repeat, reset, position, and confirmation signals.


<h2 id="level-16" className="scroll-mt-24">
  Level 16 is where I find out whether Switch itself is learned
</h2>

Switch receives its first fixed Campaign slot on **Level 16**.

The setup gives the team:

**4:00**

with:

**2 × Random Easy + Switch**

while:

**Pressure + Alarm**

are also active.

That combination makes Level 16 useful for a specific reason.

Switch is new, but the surrounding defusal load is still light enough that I can tell whether Switch itself is causing the delay.

If we need three complete rereads just to hold four colors and four numbers together, adding a harder module does not fix that.

Level 17 keeps Switch and raises the defusal mix to:

**Random Easy + Random Medium + Switch**

with:

**Alarm + Slider**

The Switch read has not become smaller. There is simply less spare attention around it.

By **Level 20**, the fixed setup can include:

**Random Easy + Maze + Switch**

with:

**Pressure + Alarm**

inside **5:00**.

That is not where I want to discover that our team still confuses the second Switch number with the second switch action.


<h2 id="push-or-return" className="scroll-mt-24">
  I leave Level 16 when one board read reliably becomes one submission
</h2>

Switch does not need to become instant before I move deeper into Campaign.

Eight source values deserve a few deliberate seconds.

What I want is a predictable run from read to Enter.

I stay around the Level 16–17 range when:

- colors and numbers regularly lose their positions;
- solving begins before all eight values have arrived;
- the return says Up or Down without identifying which physical switch;
- Enter is pressed while one position is still disputed;
- a pattern from the previous bomb keeps influencing the current one;
- a single interruption forces us to reread the board several times.

I move forward when the same basic sequence stops feeling fragile:

the colors arrive once;

the numbers arrive once;

four switch positions come back;

Blind sets the row;

Enter ends the module.

That is enough.

The solve can still take time.

What I do not carry into later levels is uncertainty about which value belongs where.

When I am deciding whether the next Campaign jump adds too much around Switch, I check the <Link href="/bombanana/levels">BOMBANANA Levels & Walkthrough</Link> before pushing into the Maze-heavy Level 20 range.

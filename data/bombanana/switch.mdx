<h2
  id="whole-state"
  className="scroll-mt-24"
>
  Switch Is One Four-Part State, Not Four Tiny Puzzles
</h2>

Switch becomes difficult the moment the team starts treating each physical switch as an independent question.

The panel carries two ordered rows of information:

**four light colors**

and:

**four numbers**

Both belong to the same state.

So when I read the panel, I keep the positions locked from left to right.

A useful call sounds like:

**“Switch. Red, Yellow, Blue, Green. Four, Three, Two, Six.”**

That gives the manual side one complete object to work with.

A call such as:

**“Red four.”**

followed several seconds later by:

**“Yellow three.”**

is much easier to corrupt.

By the time the fourth number arrives, somebody may already be solving the first switch from an incomplete state.

<h2
  id="order-matters"
  className="scroll-mt-24"
>
  The Same Four Colors in a Different Order Are a Different Problem
</h2>

There are four colors on the panel, but I do not reduce them to a bag of:

**Red + Yellow + Blue + Green**

Their positions matter.

Compare:

**Red / Yellow / Blue / Green**

with:

**Green / Blue / Yellow / Red**

Both contain the same four colors.

They do not describe the same Switch state.

That means the phrase:

**“We have all four colors.”**

is not enough information.

I need:

**first color → second color → third color → fourth color**

and the four numbers tied to those same positions.

Once somebody starts reading colors clockwise, by preference, or in the order they happen to notice them, the rest of the call can still sound plausible while pointing at the wrong physical switches.


<h2
  id="numbers-change-answer"
  className="scroll-mt-24"
>
  Keeping the Color Order Does Not Make the Old Up/Down Pattern Safe
</h2>

The strongest reason to keep all four numbers is visible in completed Switch states.

These three states share exactly the same color order:

**Red / Yellow / Blue / Green**

but their numbers differ.

Look only at the first three rows.

The color order stays:

**Red / Yellow / Blue / Green**

while the switch outputs change from:

**Down / Down / Up / Down**

to:

**Up / Up / Down / Down**

to:

**Down / Up / Down / Down**

So an answer remembered from the previous bomb is weak evidence.

The light order tells me which state I am reading.

The numbers determine what that particular state actually asks for.

The five completed setups above are useful sanity checks, not a shortcut that replaces reading the current panel. 


<h2
  id="read-packet"
  className="scroll-mt-24"
>
  I Send Eight Values Once Instead of Repairing Four Partial Calls
</h2>

Switch has a heavier input packet than most earlier modules.

Direction needs two values.

Calculator has a clear stage transition.

Switch can require the team to hold:

**4 colors + 4 numbers**

before the Up/Down answers are finished.

That creates a specific tradeoff.

Reading the whole state takes a few seconds longer at the start.

Repairing a broken partial state usually costs much more.

My callout rhythm is:

**“Switch.”**

**“Colors: Red, Yellow, Blue, Green.”**

**“Numbers: Four, Three, Two, Six.”**

Then I stop adding new bomb information until the Switch answer comes back.

This is one of the modules where starting another panel while Mute is still resolving the current state creates far more noise than useful parallelism.


<h2
  id="set-switches"
  className="scroll-mt-24"
>
  Set the Four Positions Before Enter Becomes Part of the Conversation
</h2>

The output also needs a fixed order.

I use physical positions:

**first**

**second**

**third**

**fourth**

from left to right.

An answer can therefore come back as:

**“Down, Down, Up, Down.”**

Blind sets the four switches in that order.

Only after the full physical row matches do I treat **Enter** as the next action.

Enter is important because one uncertain switch turns four mostly-correct answers into one failed submission.

If the third position is still being debated, the useful state is:

**three known + one unresolved**

not:

**“close enough, hit Enter.”**


<h2
  id="when-to-reread"
  className="scroll-mt-24"
>
  One Missing Value Is Enough to Restart the State Call
</h2>

There are several moments where I would rather spend five seconds rereading than guess.

### The color order was interrupted

Start the four colors again from the left.

### One number is disputed

Read all four numbers again.

A Switch condition can depend on information elsewhere in the same state, so repairing one isolated number while everybody remembers a different version of the other three is risky.

### Nobody remembers which switch answer belongs to which position

Stop moving switches.

Return to:

**first / second / third / fourth**

and rebuild the output row.

### Enter was pressed and the panel did not clear

The old state is no longer something I trust from memory.

Look at what the module shows now before repeating the previous pattern.


<h2
  id="real-wall"
  className="scroll-mt-24"
>
  The Real Wall Is Usually State Integrity
</h2>

Switch looks like a logic-heavy module because eight source values can be active at once.

In practice, many failures happen before the manual decision itself.

A number gets attached to the wrong light.

The fourth value arrives while somebody is still repeating the second.

One player starts setting switches before the final answer is complete.

A previous Up/Down pattern survives into a new board because the colors look familiar.

Those failures all share one cause:

**the team stopped agreeing on one complete current state.**

The fastest fix is not usually speaking faster.

I slow the first call down enough that the full state reaches the manual intact.

Once the four output positions are returned, execution can be quick.


<h2
  id="two-resets"
  className="scroll-mt-24"
>
  “Repeat One” and “Restart the State” Solve Different Problems
</h2>

Sometimes I genuinely miss one word.

If the call was:

**“Red, Yellow, Blue, Green”**

and only Green was hard to hear, repeating Green is fine.

The larger problem begins when nobody knows whether the disagreement is local.

Was the second number wrong?

Did two numbers get swapped?

Was the color order already different?

At that point I need the entire eight-value packet again.

That distinction is useful beyond Switch, but Switch is where it becomes expensive enough to force the habit.

If the team repeatedly cannot tell whether it needs one repeat or a full reset, the broader relay system belongs in the <Link href="/bombanana/roles">BOMBANANA Roles Guide</Link>.


<h2
  id="level-16"
  className="scroll-mt-24"
>
  Level 16 Is the First Fixed Switch Checkpoint
</h2>

In the full Campaign, Switch first gets a fixed slot on **Level 16**.

That bomb gives the team:

**4:00**

with:

**2 × Random Easy + Switch**

and:

**Pressure + Alarm**

The important detail is not simply that Switch appears.

By Level 16, the game has already spent fifteen levels teaching the team how to move information under Chaos pressure.

Switch now asks whether that communication system can hold a larger state.

Level 17 keeps Switch and raises the defusal mix to:

**Random Easy + Random Medium + Switch**

with:

**Alarm + Slider**.

Level 20 goes further:

**Random Easy + Maze + Switch**

with:

**Pressure + Alarm**

inside **5:00**.

That progression gives me a useful checkpoint.

If Switch still requires three or four complete rereads on Level 16, I would not use Level 20 as the place to learn it.


<h2
  id="push-or-return"
  className="scroll-mt-24"
>
  I Push Once the State Survives One Clean Relay
</h2>

I do not need Switch to become instant.

It carries more information than the early modules, so some deliberate pacing is reasonable.

What I want before pushing deeper is reliability.

I stay with the Level 16–17 range when:

- colors and numbers regularly become detached;
- somebody starts solving before all eight values arrive;
- physical positions are returned without saying first through fourth;
- Enter gets pressed with one disputed switch;
- the previous bomb's pattern keeps influencing the next one.

I move on when one complete read reliably produces one complete four-switch answer.

At that point, a longer solve time is manageable.

Repeated state corruption is not.

For the surrounding Campaign route, first appearances, and the jump from Level 16 to Maze-heavy Level 20, the <Link href="/bombanana/levels">BOMBANANA Levels & Walkthrough</Link> owns the full progression.

<h2
  id="which-module"
  className="scroll-mt-24"
>
  Identify the module before sending any values
</h2>

When several panels are active, I name the module before anybody starts calling numbers, colors, or symbols.

A short call such as **“Green, two”** is not enough when one player is reading Direction and another is waiting on a Calculator LED.

The three solver inputs are deliberately different:

- **Cable / Wire:** cable count, active light, cable colors from left to right
- **Direction:** active light, Braille number
- **Calculator:** equation first; the new LED is used only after the raw result has been entered

If the panel does not match one of those three input patterns, I do not try to force it into the tool.

The stage indicator is worth watching because a successful input does not always remove the panel.

If the module advances, I drop the old state and read the new one before entering anything else.


<h2
  id="cable"
  className="scroll-mt-24"
>
  Cable / Wire needs the complete panel state
</h2>

For Cable, I collect three things before solving:

**cable count → active light → cable colors from left to right**

The cable count matters because 3-cable and 4-cable boards do not use the same rule set.

The order matters for a different reason: once the target cable has been identified, Blind still needs the physical cable position on the bomb.

That is why I enter the colors in the same left-to-right order they appear on the panel rather than treating them as an unordered list.

<Image
  src="/images/bombanana/bombanana-cable-module-manual.webp"
  alt="BOMBANANA Cable Module manual showing the three-cable and four-cable solve table"
  width={1600}
  height={900}
  className="my-8 rounded-xl"
/>

If the solver says the required target color is missing or appears more than once, I reread the panel instead of guessing which cable was intended.

For the complete mapping, worked examples, and the safest way to translate the result into a physical cut, use the <Link href="/bombanana/wire">BOMBANANA Cable / Wire Guide</Link>.


<h2
  id="direction"
  className="scroll-mt-24"
>
  Direction is one light, one Braille number, one press
</h2>

Direction has a compact input:

**active light + current Braille number**

The solver returns one direction:

**Up, Down, Left, or Right**

I use that answer for the current stage only.

<Image
  src="/images/bombanana/bombanana-direction-module-manual.webp"
  alt="BOMBANANA Direction Module manual showing the active-light and Braille-number direction table"
  width={1600}
  height={900}
  className="my-8 rounded-xl"
/>

After the press, I immediately look at the panel again.

If the light, Braille number, or stage has changed, I treat it as a new state and solve again.

The current Direction table uses Braille numbers **1, 2, 3, 4, 5, 6, 7, and 9**. If I think I am seeing an 8, I reread the pattern before pressing anything.

The lookup itself is usually fast. The more dangerous problem is letting different players use different meanings for left and right.

For the full Blind / Deaf / Mute perspective and callout convention, use the <Link href="/bombanana/roles">BOMBANANA Roles Guide</Link>.


<h2
  id="calculator"
  className="scroll-mt-24"
>
  Calculator has two separate input stages
</h2>

Calculator is the module where entering information too early causes the most confusion.

The first state gives me an equation.

At this point I do **not** need a colored LED.

I solve the equation and enter the **raw result** first.

If that input is accepted, the Calculator moves into its second state.

Now I need:

**the new LED + whether the raw result was odd or even**

That combination gives the final single-digit key.

<Image
  src="/images/bombanana/bombanana-calculator-module-manual.webp"
  alt="BOMBANANA Calculator Module manual showing the odd-even and active-light answer table"
  width={1600}
  height={900}
  className="my-8 rounded-xl"
/>

I keep the two values mentally separate:

**raw result** advances the Calculator.

**final key** finishes the Calculator.

If the equation result was accepted and the panel is still active, I do not enter the same number again. I read the new LED and continue from stage two.

The <Link href="/bombanana/calculator">BOMBANANA Calculator Guide & Solver</Link> owns the complete answer table, worked examples, shuffled-keypad warning, and the full explanation of why the LED appears late.


<h2
  id="chaos"
  className="scroll-mt-24"
>
  Chaos is not an input for this solver
</h2>

The solver handles modules that return a specific answer from a specific state.

Chaos can interrupt that solve when a danger control needs attention. Stabilize the danger, then return to the defusal panel and confirm its current state before using an older answer.

For Chaos priority, stacked hazards, and when I interrupt or resume a solve, use the <Link href="/bombanana/chaos">BOMBANANA Chaos Guide</Link>.

<h2
  id="stale-answer"
  className="scroll-mt-24"
>
  A correct answer can become stale after one input
</h2>

Once the team gets faster, stale answers become more dangerous than slow lookups.

The sequence is simple:

the solver returns an answer;

the correct input is made;

the module advances;

somebody repeats the old answer;

Blind acts on it again.

Nothing was wrong with the original lookup. It belonged to the previous state.

Calculator has the same risk when the raw result is accepted and the useful information changes from an equation to a colored LED.

I treat every successful input as a checkpoint.

After a press, cut, or accepted Calculator result, I check:

**Did the module clear?**

If yes, I drop every value attached to it.

If no, I read the current panel again before using another answer.

That habit matters more as several modules begin competing for attention at the same time.


<h2
  id="bad-input"
  className="scroll-mt-24"
>
  If the result looks impossible, reread the input first
</h2>

The solver can only answer the state entered into it.

If the result does not fit the panel, I do not immediately assume the rule table is wrong.

For Cable, I check:

- whether there are 3 or 4 cables;
- the active light;
- every cable color;
- the left-to-right order.

For Direction, I check:

- the active light;
- the Braille number;
- whether the panel has already advanced.

For Calculator, I check:

- both equation values;
- the operator;
- the raw result;
- whether the current LED belongs to stage two.

I also restart the callout if two modules were being described at the same time.

One extra fact rarely repairs a state that was already mixed together.

When the input packet becomes unreliable, I read the panel again from the beginning.


<h2
  id="communication"
  className="scroll-mt-24"
>
  The solver cannot repair a broken information relay
</h2>

There is a point where entering the same state into the tool again stops helping.

If the lookup is correct but Blind still cannot identify the physical action, the problem is no longer the rule table.

If Direction is solved but players disagree about whose perspective the answer uses, another lookup changes nothing.

If Calculator reaches stage two but the raw result and final key are both being passed around as unlabeled numbers, faster arithmetic will not fix the run.

Those are communication failures.

That is when I switch to the <Link href="/bombanana/roles">BOMBANANA Roles Guide</Link>.

It covers the Blind / Deaf / Mute relay, physical-position language, perspective conventions, keeping module states separate, and deciding when swapping roles is more useful than another retry.


<h2
  id="manual"
  className="scroll-mt-24"
>
  Not every module needs the same kind of tool
</h2>

Cable, Direction, and Calculator work well here because their current states can be reduced to short deterministic inputs.

Other BOMBANANA modules ask the team to do something different.

A panel may depend on:

- recognizing a symbol;
- hearing or reproducing a sound;
- remembering a sequence;
- reading several values together;
- tracking multiple stages;
- managing danger instead of clearing it.

That includes modules such as **Color Slider, Symbol, Piano, Soundboard, Maze, Morse, and Monkey-Says**.

For those panels, I use the relevant manual guidance instead of trying to translate them into a Cable, Direction, or Calculator input.

If I am still learning where a module appears in Campaign progression, I use the <Link href="/bombanana/levels">BOMBANANA Levels & Walkthrough</Link>.

If I need the broader game route rather than one exact lookup, I return to the <Link href="/bombanana">BOMBANANA Guide</Link>.


<h2
  id="during-run"
  className="scroll-mt-24"
>
  How I use the solver while the timer is running
</h2>

During a bomb, I do not read this page from top to bottom.

I identify the active module and send the smallest complete input packet it needs.

For Cable:

**count → LED → colors from left to right**

For Direction:

**LED → Braille number**

For Calculator:

**equation first**

then, if the module remains active:

**new LED + parity of the raw result**

I use the returned answer once and look at the bomb again.

If the panel has changed, I solve the new state rather than carrying the previous answer forward.

If I cannot identify what information the module needs, I stop guessing and use its manual guidance.

If the rule is understood but the answer keeps getting lost between players, I move to the <Link href="/bombanana/roles">Roles Guide</Link>.

If the module is no longer the problem and I want to know what the Campaign introduces next, I use the <Link href="/bombanana/levels">Levels & Walkthrough</Link>.

The solver is for one very specific moment:

**I know which module this is, I can read its current state, and I need the next correct input now.**
